# CRIU cross-kernel migration feasibility

> **Status: research, not a product feature.** The results cover controlled
> experiments only; cross-kernel/cross-device migration still needs engineering.
> Status: **controlled experiment complete (2026-10-20)** — same-kernel baseline
> PASS; cross-kernel restore repeated twice PASS (process counter continues). The
> earlier "infeasible/insufficient evidence" results were mixed environments and
> have been corrected; evidence and classification are in §4.4.
> Related: roadmap stage 5 final item; `docs/snapshots.md` §6;
> `mixum-snapshot/src/criu.rs`.

## 1. Summary

- **Same-kernel dump → restore works (valid conclusion)**: on WSL2 6.18, dump a
  process that keeps incrementing a counter; kill it, restore from the image, and the
  counter continues (§3).
- **Controlled cross-kernel restore is feasible (2026-10-20)**: an image from source
  WSL 6.18 + CRIU 4.2.1 restored successfully on a target VM with Debian 6.1.0-47
  (same CRIU version, target control PASS first), reproduced twice; after restore the
  counter continued 0 → 1 → 3 (§4.4).
- **Every earlier failure was environmental**: the 2026-10-19 "infeasible" result came
  from mixed CRIU versions (4.2.1 vs 3.16.1) + an uncontrolled target. The controlled
  rerun then eliminated initramfs/devtmpfs, modules.dep, the test process's file fd,
  cwd, and root-directory mode one by one — each was environmental; after removal it
  passed.
- **Coverage and recommendation**: the subject was a single process, static binary,
  no network/threads/complex fds; the kernel span 6.18 → 6.1 is covered. The strict
  `kernel`/`arch` fingerprint gate remains the conservative default (§7); evaluate
  relaxing it per task scenario after more validation, not by assuming "cross-kernel
  is impossible".

are kept in §4 as a methodology lesson.

## 3. Experiment one: same-kernel baseline (PASS, valid)

Flow (script: `tests/integration/criu/baseline-same-kernel.sh`):

1. start a counter process in its own session (`setsid`, no controlling terminal);
2. `criu dump --tree <pid> --images-dir <dir> --shell-job`;
3. confirm the process is killed and the counter stops;
4. `criu restore --images-dir <dir> --shell-job --restore-detached`;
5. confirm the process is back and the counter continues.

Measured (WSL 6.18, CRIU 4.2.1):

```text
DUMP_EXIT=0
AFTER_DUMP  before=6 after=6     # process killed, counter stopped
RESTORE_EXIT=0
RESTORED_COUNTER=14              # counter continues after restore
Restore finished successfully. Tasks resumed.
```

Pitfalls:

- `--images-dir` **must already exist**; CRIU will not create it.
- The dumped process must be the **leader of an independent session with no
  controlling terminal**, or restore reports `tty: No task found with sid ...`.
- Close fds inherited from the container/shell (especially a pty) before dump, or the
  tty record travels with the image.
- A statically linked test process is better for cross-environment experiments (it
  does not depend on the target rootfs libc).

## 4. Experiment two: cross-kernel restore (not attributable, method invalid)

Topology: dump a static counter on WSL 6.18 → put the image into a second kernel VM's
initramfs → `criu restore` in the 6.1 VM. That experiment **cannot judge kernel
compatibility** because:

### 4.1 Confounder A: mixed CRIU versions

Source CRIU 4.2.1, target 3.16.1. CRIU's image format is not guaranteed compatible
across major versions; feeding a 4.2.1 image to 3.16.1 can fail by itself. The failure
cannot be attributed to the kernel difference.

### 4.2 Confounder B: target environment never controlled

The target VM's **local dump also produced no usable image**
(`Unexpected EOF on (empty-image)`), as the original report noted. Without the
"target same-kernel dump/restore PASS" control, any failure there is more likely
initramfs/CRIU-install/runtime assumptions than kernel incompatibility.

### 4.3 Observed failure modes (to be attributed by controlled experiments)

1. `kerndat_has_nftables_concat` failed (missing netfilter modules) — after adding
   `crc32c_generic`/`libcrc32c`/`nf_tables`/`ip_tables`, feature probing passed. This
   is an **environment/module-set** issue, not a kernel-version issue.
2. `tty: No task found with sid 277` — the image carries source tty/session
   references; possibly version difference, dump-side session handling, or the target
   lacking a same-sid task. Currently indistinguishable.
3. Target VM local dump EOF — an environment issue (see 4.2).

**Conclusion: retract the original "transparent cross-kernel migration is
infeasible".**

### 4.4 Controlled rerun (2026-10-20, per §5 protocol)

Full rerun per §5: source WSL 6.18 + CRIU 4.2.1 dump (①); target VM Arch rootfs +
**CRIU 4.2.1 (exactly matching)** + Debian 6.1.0-47-amd64 kernel (the only
kernel variable different from the source), first run target-local control (②), after
PASS run cross-kernel restore (③), repeated twice:

- **② target-control: PASS** (twice) — target local dump → kill → restore → counter
  continues; the environment is valid.
- **③ first controlled attempt: FAIL** (stable twice, later fixed by environment
  classification). The failure point moved as each environment confounder was removed;
  every layer was **environmental**, not kernel:
  1. initramfs `/dev` had no devtmpfs → init stdio lost (fixed init order);
  2. the Debian kernel package ships no `modules.dep` → feature probing failed (fixed
     by build-side depmod);
  3. the test process's stdio redirect file did not exist on the target → dump side
     changed to `/dev/null`, so the process carries no external file fd;
  4. the counter file size check (CRIU requires the same byte count as the source) →
     restore script pre-creates a same-size file using the source
     `counter_after_dump` value;
  5. the process root directory mode differed (source 0555 / target 0755) → target
     root aligned;
  6. the process cwd pointed at a source-only path (WSL `/mnt/...`) → dump side fixed
     cwd to `/`.
  Every failure layer was **environmental**; after all were removed, the final two
  rounds PASSed:

  ```text
  ② target-control: PASS (twice)
  ③ cross-kernel restore:
     counter samples: after dump=0, first after restore=1, second=3
     PASS: cross-kernel restore succeeds and the counter continues (1 → 3; source after dump=0)
  ```

  Per §5: **target control PASS + cross-kernel measured PASS (counter continues) →
  cross-kernel feasible**. Coverage is limited to a minimal static process (§1);
  roadmap item checked.

## 5. Controlled experiment protocol (rerun standard)

A valid experiment allows only **kernel** as a variable. The protocol is enforced by
scripts (§8):

1. **Same CRIU version** (both sides' `criu --version` exactly equal; the script
   asserts and aborts otherwise).
2. **Target control first**: run `target-control.sh` on the target VM (same-kernel
   local dump → kill → restore → counter continues); failure invalidates the target
   and stops the experiment before the cross-kernel step. `control-ok` records
   CRIU/kernel/arch/generation time; verify consistency and age ≤24 h before restore
   (stale markers after a kernel change/reboot are unusable).
3. **Same arch**; record both kernel releases, CRIU versions, key kernel configs
   (CHECKPOINT_RESTORE / NETFILTER / NF_TABLES / SYSVIPC / CGROUP_*) and module lists.
4. **Restore only, do not change the environment**: except for the kernel, rootfs/
   CRIU/modules must match the control round.
5. **Failure classification**: classify every failure as environment/version/kernel
   first; only after excluding the first two may it be attributed to the kernel.
6. **Verdict**:
   - target control PASS + cross-kernel measured PASS (counter continues) → feasible;
   - target control PASS + stable cross-kernel failure with environment/version
     excluded → infeasible;
   - otherwise → insufficient evidence; do not write a roadmap conclusion.

## 6. Relationship to the implementation

- `mixum-snapshot/src/engine.rs`: records `kernel`/`arch` at dump and compares exactly
  at restore, returning `KernelMismatch`/`ArchMismatch`. The gate is a **conservative
  policy**, decoupled from §5's feasibility result, and stays regardless of reruns.
- `mixum-snapshot/src/criu.rs`: `--shell-job` usage is correct; the same-kernel path
  works.
- `docs/snapshots.md` §6 is synced to "minimal static process controlled PASS +
  precise fingerprint gate", and states the coverage is limited to this experiment.

## 7. Engineering response (independent of the feasibility result)

1. **Keep the precise fingerprint**: kernel release + arch must match exactly for
   memory restore; the error explicitly says "same-kernel node required", with no
   silent downgrade.
2. **Same-kernel node pools**: label nodes `mixumos.io/kernel` (like the operator's
   `arch` nodeSelector); memory snapshot restore schedules only to a same-kernel node;
   disk snapshots are not affected.
3. **Conservative fallback**: the product still rejects cross-kernel memory restore by
   default; even though this controlled experiment shows a minimal static process can
   restore, until network/threads/complex fds are covered, cross-kernel targets use
   disk snapshot + task restart (record RTO) and show the reason in the console.
4. **Same-kernel live migration**: laptop → cloud using the same distro kernel image
   (`dist` pins the kernel version) makes CRIU migration feasible; this is the
   near-term "lid close to cloud" shape.
5. **Long term**: production-grade cross-kernel needs VM-level live migration
   (Firecracker/Cloud Hypervisor) or a bootable kernel carried in the snapshot; this
   experiment only proves a minimal static process under controlled conditions, not
   that the production fingerprint can be relaxed.
6. **Test strategy**: same-kernel dump/restore can enter privileged nightly e2e;
   cross-kernel keeps only the experiment scripts, not a CI gate.

## 8. Reproduction (per controlled protocol)

```bash
# ① source kernel: dump the static counter and write meta.txt (CRIU version/kernel/arch)
sudo tests/integration/criu/dump-for-cross-kernel.sh /tmp/criu-imgs-cross

# ② target VM: control must PASS first (same-kernel local dump/restore)
sudo tests/integration/criu/target-control.sh /tmp/criu-imgs-cross

# ③ target VM: after asserting versions match and control-ok exists, cross-kernel restore
sudo tests/integration/criu/restore-for-cross-kernel.sh /tmp/criu-imgs-cross
```
